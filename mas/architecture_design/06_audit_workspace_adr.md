# ADR-P5-02 — The iterative audit workspace

**Status:** ACCEPTED (2026-08-21) · solutions-architect
**Supersedes:** nothing. **Extends:** ADR-05 (per-endpoint model routing), FR-009/011/014, BR-10.
**Owner request:** live heuristics on edit (shipped) → the AI audit re-runs automatically after an
edit-idle delay *or* on demand, pausable → every run keeps its own result tab and the exact source
it analysed → recommended fixes can be applied to the source → any version can be restored.

---

## 1. NFRs this design is bound by (measured, not asserted)

These come from the code as it exists, not from aspiration. They are what make the naive reading
of the request ("re-run the audit whenever the user stops typing") the wrong design.

| # | Constraint | Measured value | Source |
|---|---|---|---|
| **N1** | The AI audit runs on the **expensive** model | `AUDIT_MODEL = claude-opus-4-8`, `max_tokens: 1500` | `workers/portfolio-agent/src/routes/audit.js:16,49` |
| **N2** | Per-IP audit budget | **10 requests per window**, then 429 | `rateLimit.js` `BUDGETS.audit = 10` |
| **N3** | The heuristic pass is free and instant | pure, regex-scale, no network, sub-ms on a contract | `src/lib/auditHeuristics.js` |
| **N4** | The audit already degrades, per run | Opus → Qwen2.5-Coder → KV recorded → graceful note | `routes/audit.js` |
| **N5** | Source cap | 24,000 chars, client + Worker mirrored | `auditClient.js SOURCE_CAP` |
| **N6** | No client-side persistence is permitted without consent | site is deliberately cookieless (ePrivacy Art 5(3)) | ADR-P5-01, `COMPLIANCE_RESEARCH.md` Q2 |

**The decisive one is N1 × N2.** A 3-second idle-triggered re-run fires an Opus call every time the
user pauses to think. A person editing a contract for one minute can exhaust the entire per-IP
budget and spend the rest of their visit on the recorded fallback — the auto-rerun would *degrade
the very thing it was added to improve*. Auto-rerun is therefore not a timer; it is a **policy**.

## 2. Decision 1 — auto-rerun is a gated policy, off by default

**Selected:** an explicit policy function with four gates, evaluated on an idle timer.

```
enabled ∧ ¬paused ∧ (draft ≠ lastAnalysedSource) ∧ heuristicFingerprintChanged ∧ validSource ∧ budgetRemaining
```

| Option | Pros | Cons | NFR alignment |
|---|---|---|---|
| A — plain idle debounce (the literal request) | trivial; feels magic | burns N2 in ~1 min of editing; every pause costs an Opus call (N1) | **violates N1/N2** |
| B — gated policy, opt-in (**selected**) | costs a call only when the *screen* actually changed; user keeps manual control | one more control on screen; a changed comment won't re-run | satisfies N1/N2, keeps N4 |
| C — manual only (status quo) | cheapest | ignores the request; the loop stays clunky | fails the requirement |

**Selected B because N1/N2**: the free deterministic layer (N3) decides whether the expensive layer
(N1) is worth spending. If the heuristic fingerprint — the ordered set of `id:line:severity` — is
unchanged, the model has nothing new to see, so no call is made. Renaming a variable does not buy
an Opus call; introducing a reentrancy does.

**Off by default** because a visitor did not ask to spend a shared budget, and because the honest
default on a page about restraint is restraint. The toggle states its own cost in the UI.

**Risk:** a user turns it on, edits heavily, and hits 429 anyway. **Mitigation:** the client counts
its own runs against the known budget and shows remaining/spent, stopping the auto-policy (never
the manual button) one short of the cap so the user always keeps a deliberate run in hand.

**Trade-off accepted:** an edit that changes semantics without changing the fingerprint (e.g.
inverting a `require` condition) will not auto-trigger. The manual button is always live and the UI
says "no change the screen can see" rather than pretending it looked.

## 3. Decision 2 — fixes are deterministic remediations, not model output

**Selected:** fixes are generated by the **heuristic layer** (a pure `fixFor(finding, source)`),
never parsed out of the model's prose.

| Option | Pros | Cons | Verdict |
|---|---|---|---|
| A — apply patches parsed from the narrative markdown | fixes anything the model can describe | ambiguous (which fence is the fix?); hallucination applied straight into the user's code; needs a new tag contract; unusable offline | rejected for now |
| B — deterministic fix per detector (**selected**) | pure + testable; works offline; ships with the detector that raised it | only covers patterns we detect | selected |

**Selected B because N3/N4 and BR-10.** A detector that can recognise a pattern can express its
remediation; that fix is then a pure function, unit-testable with a before/after, and available
when the Worker is down — matching the console's existing floor.

**The property that makes this worth building:** after a fix is applied, the free heuristic pass
re-screens the *result* and the UI reports whether the finding **actually cleared**. The tool does
not claim it fixed anything — it applies a change and then shows you the re-screen. That is the
site's own thesis (*reproduce, don't assert*) turned on itself. A fix that fails to clear its own
finding is displayed as exactly that, which is more instructive than one that silently succeeds.

**Never auto-apply.** Every fix is one explicit click and is always revertible (§4).

Option A stays open: when the Worker's audit prompt is extended to emit a structured
`[PATCH: {...}]` under the existing tag protocol, model fixes can join the same apply/re-screen/
revert machinery — labelled *model-suggested*, distinct from *rule-derived*. Out of scope here.

## 4. Decision 3 — the state model: a draft, checkpoints, and runs

Three distinct things, which the current console conflates into one `source` string:

```
draft        the live editor text. Changes per keystroke. Never versioned per keystroke.
versions[]   append-only checkpoints. v1 = "Original" and is never removed.
             created ONLY by: applying a fix, restoring a version, or starting a run.
runs[]       append-only. Each pins { source, narrative, degraded, status }.
```

**Corrected during build (W-1):** the draft of this ADR had runs pinning their *findings* too.
They don't — findings are a pure function of the source, so a run tab re-derives them from
`run.source` and gets a deterministic, identical answer. Storing them would have been storing
derived state, which is the precise bug that made this console ignore edits in the first place.

**Added during build (W-1), after an E2E caught it:** *any* action that replaces the draft first
pins the current draft as a checkpoint (`pinDraft`). Without it, pasting your own contract over
the sample and then applying a fix left "Original" pointing at the demo contract — undo could not
reach the thing you were actually working on. It now applies uniformly to run-start, apply-fix,
and restore.

- **Versions ≠ undo history.** Keystrokes do not create versions; a thousand-entry list is not a
  history a person can use. A checkpoint is created at the moments that carry meaning — a fix
  applied, a version restored, an analysis run — so every entry in the list is somewhere a reader
  would actually want to go back to.
- **Runs are the tabs.** Each run tab carries its own analysis *and* the source that produced it,
  so an old analysis can never be read against new code. "Restore this version" moves that run's
  source back into the draft (creating a new checkpoint — restore is additive, never destructive).
- **The original is permanent.** v1 is created before the first edit and cannot be superseded;
  "revert to original" is always one click, satisfying the request's "keep the original code as
  well as the original analysis".

State transitions live in **one pure module** (`auditWorkspace.js`) so the whole loop — apply fix,
re-screen, checkpoint, run, restore — is testable without a DOM, a timer, or a network.

## 5. Honesty rules (binding — these are FR-014/BR-10 surfaces)

1. **Every run tab carries the disclaimer and its own provenance label** (live model vs recorded
   fallback). Provenance is per-run, not per-page: run 1 may be live and run 3 recorded.
2. **A run tab whose source ≠ the draft is labelled stale**, with the version it analysed named.
3. **An applied fix is labelled `rule-derived`**, never "AI fix", and is followed by a re-screen
   that states whether the finding cleared. No fix is described as making the contract safe.
4. **Nothing is applied without a click**, and everything applied is revertible.
5. **The auto-run toggle states its cost** and why it is off by default.
6. **A skipped auto-run says why** (paused / no visible change / budget) rather than silently not
   running, which would read as "the analysis agrees with your edit".

## 6. Red-team

| # | Challenge | Finding → Mitigation |
|---|---|---|
| 1 | 10× load | Auto-rerun is the amplifier: it turns one visitor into N Opus calls. Gated by §2 (fingerprint + idle + budget), off by default, and the client stops one short of the cap. |
| 2 | Single point of failure | The Worker/Opus. But the *iteration loop itself* — edit, screen, fix, re-screen, checkpoint, restore — is 100% client-side and pure. With the Worker down the workspace still works; only the narrative degrades (N4), per run, labelled. |
| 3 | Weakest security control | Writing generated text into the user's editor. It is client-side only, never executed, never sent anywhere; the real exposure is *trust*, mitigated by determinism + mandatory re-screen + `rule-derived` labelling. |
| 4 | Vendor down 4 hours | Runs degrade to Qwen → recorded → note, each labelled. Versions/fixes/restore unaffected. No dead-end. |
| 5 | Partially-addressed compliance | FR-014's disclaimer was rendered **once per page**; with N runs on screen it must render **per run tab**. Fixed in this design, not documented around. |

## 7. Accepted technical debt

- **Fixes are line/regex-based, not AST-based.** No Solidity parser is going into this bundle
  (N1-adjacent: bundle budget). Consequence: fixes are conservative, one pattern at a time, and
  *each one is verified by the re-screen* rather than trusted. A fix that cannot be expressed
  safely for a given source is not offered — the finding simply has no fix button.
- **No persistence across reload.** In-memory only, deliberately: persisting a draft is storage on
  terminal equipment (N6) and the site's cookieless posture is what makes its consent story simple.
  A reload starts clean, which is stated in the UI rather than discovered.
- **The `[PATCH]` tag contract for model-suggested fixes is deferred** (§3), not designed here.
